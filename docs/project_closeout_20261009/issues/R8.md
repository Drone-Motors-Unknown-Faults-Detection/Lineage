# R8：先 profiling，再決定 CSV cache 或 k-NN 向量化

來源：#30 PERF-001/PERF-002；main `4d1858b830890a761af1dc550e74010db8a4b5f5`。`core/data.py:load_pools` 重讀 CSV；`core/openset.py` 逐類 kneighbors。這是結構線索，尚無本輪 profiling，不宣稱主要瓶頸。

## 最小重現與範圍

事前固定 fixture／可讀正式資料版本、seed、warmup與重複次數，量測 load walltime／peak memory、scaler/fit/cal時間、score batch大小、known類數與reference大小。冷／熱快取分開，保存 Python/OS/packages/CPU資訊；不把不同硬體的舊秒數當本輪數字。

範圍：先新增獨立 profiling 入口與工程契約，走 setup_run。證據顯示值得改才新增內容SHA鍵 cache或neighbor批次化；不能先實作再反推profiling理由。正式 data與歷史結果唯讀，不更換模型或近似演算法。

## 驗收

- [ ] 固定量測契約、至少重複量測與全部樣本，保存walltime/memory及方法設定，不只最好一次。
- [ ] 若採 cache，同size/mtime異bytes不能誤用，副本別名／版本失效與portable/private政策完整。
- [ ] 若向量化，相同輸入/seed下 score/classify/threshold逐筆配對在事前容差內，平手／空batch／不同類大小有fixtures。
- [ ] 說明改善／無改善與成本；數值不變、完整回歸、CLI、PR合main再驗收。

無實測改善也保留負面結論；不藉 profiling 宣稱模型準確率提高。
